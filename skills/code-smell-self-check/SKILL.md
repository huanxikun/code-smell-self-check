# 代码坏味道自查

按已定义的规则检查用户指定代码；未指定时检查当前改动及必要的调用上下文。仅请求自查时报告问题和建议，不直接修改代码。

## 检查规则

### 1. 命名准确体现业务含义

核心原则：好的命名体现业务含义。让读者无需展开实现，就能理解代码在做什么；进一步表达业务意图，而非容易变化的实现细节。优先沿用项目和业务领域已有的术语，不凭名称猜测业务职责。

#### 1.1 不精准的命名

- 结合实现和调用方，检查名称是否过于宽泛、遗漏关键动作，或暗示了实际未执行的行为。
- 方法名应准确表达实际动作；变量和参数名应说明其在当前业务中的角色。
- 区分查询、状态标记、流程启动和实际执行，不用模糊名称混淆它们。

示例：`chapterTranslation` 只能让人联想到“章节翻译”，无法说明具体动作。如果仅将章节标记为“翻译中”，使用 `markChapterAsTranslating`；如果实际启动翻译流程，可使用 `startTranslation`。不要把仅更新状态的方法命名成执行完整翻译的动作。

#### 1.2 用实现细节代替意图的命名

- 当集合类型不影响业务含义时，优先用 `books`，而不是 `bookList`；否则从 List 改为 Set 后，名称可能继续暗示错误的类型。
- 依赖名优先表达职责。业务代码需要的是缓存能力时，可用 `bookCache` 表达职责，而不是用 `redisBookStore` 绑定 Redis 实现。
- 如果技术名词遮蔽业务意图，检查是否缺少清晰的领域概念或职责边界；不要机械地只改名。
- 技术术语不是一律禁止。Redis 适配器、存储实现、协议代码等确实需要区分技术实现的位置，可以保留准确的技术名称；业务契约确实依赖集合顺序等特性时，也应清楚表达。

缓存示例：在 `getByIsbn` 中先读 `redisBookStore`，未命中再加载并回填，说明此处可能把查书意图与缓存实现混在一起。结合项目现有机制，评估是否通过缓存职责抽象或缓存注解隐藏实现细节，使方法突出“按 ISBN 获取图书”。普通 `@annotation` 并不自动提供缓存；注解方案依赖框架支持，不能只凭出现 Redis 就要求新建接口、引入框架或改成注解。

#### 1.3 用业务角色消除歧义

- 同一种基础类型可能代表不同角色，名称应表达区别。不要让读者仅凭 `int`、`long` 或 `userId` 猜测业务含义。
- 例如 `approveChapter(int chapter, long userId)` 中，如果已确认 `userId` 表示审核人，改为 `reviewerUserId`；如果 `chapter` 表示章节号，改为 `chapterNumber`。如果实际是章节 ID，应使用 `chapterId`。
- 角色必须通过业务契约、实现或调用上下文确认；无法确认时指出歧义，不擅自认定为审核人、作者或操作人。

### 2. 英语命名准确、规范且一致

结合标识符的用途检查英语，不把自然语言句子的语法机械套用于代码。遵循项目语言、框架和团队命名规范。

#### 2.1 语法结构与代码角色匹配

- 类名通常使用名词或名词短语，表示对象或概念；表示动作的方法名通常使用动词或动宾短语。
- 表示“完成翻译”动作的方法应命名为 `completeTranslation`，而不是 `completedTranslation`。
- `completedTranslation` 作为“已完成的翻译”这一结果对象的变量名可以成立；过去分词也可以合理描述状态或事件。不能只凭出现过去式或过去分词就判错。
- 属性、谓词、事件处理器和框架约定的入口按其实际角色判断，不强迫所有可调用对象改成动宾结构。

#### 2.2 词汇符合业务语境

- 不只看词典直译，要核对词汇在当前业务中的含义，以及产品文档、领域模型和团队现有用法。
- 如果表示章节内容审核，`chapterReviewStatus` 通常比 `chapterAuditStatus` 更贴切；如果实际表示审计、合规核查等业务，`audit` 可能准确，不机械替换。
- 同一业务概念使用一致的词汇，不用多个近义词随意混称；不同概念也不要为了统一名称而合并含义。
- 优先查阅团队已有词汇表。缺少公认译法时，提出需与产品或领域负责人确认的候选词及含义；确认后记录“业务概念、英文术语、含义和适用范围”，作为团队词汇表条目。不要把个人猜测当成已确认术语，也不因自查擅自新建团队规范。

#### 2.3 拼写正确

- 检查单词错拼、字母颠倒、遗漏及同一词的拼写不一致。例如表示“排序字段”的 `sortfiled` 应修正词根为 `sortField`，或按项目规范写为 `sort_field`；`filed` 本身是英语单词，但不是这里的 `field`。
- 区分真正拼错与专有名词、业务术语、标准缩写和外部接口既定字段。现有拼写检查工具只能提供线索，仍需结合上下文判断。
- 建议修改公开 API、持久化字段或协议键名时，标明兼容性影响；不要把它当成仅修改局部变量的简单重命名。

#### 2.4 避免拼音和不清晰的简写

- 英语命名中避免用拼音代替业务含义，也避免随意截取单词或拼接首字母，使读者必须猜测原词。
- 优先使用完整、清晰的业务单词。团队约定且读者普遍理解的缩写（如 `ID`、`ISBN`、`HTTP`）可以保留，并遵循项目大小写规范。
- 检查团队是否已有命名规范和词汇表；评审时对照它们检查新增名称。缺少约定时给出具体建议，不把自己的偏好当成团队规则。

### 3. 重复代码

核心原则：Don't Repeat Yourself（DRY）。每一处知识都应有单一、明确、权威的表达。重点识别同一业务规则或处理流程的多处维护，避免修改一处却遗漏其他位置。

#### 3.1 复制粘贴的代码

- 查找相同或轻微修改的代码块，比较它们是否表达同一规则、校验、计算或处理流程。
- 不只比较文本；变量名、字面值或调用对象不同，也可能重复了同一知识。
- 指出具体重复位置，以及业务变化时需要同步修改哪些地方。复制粘贴造成的遗漏、分支行为不一致应明确说明。

#### 3.2 结构重复的代码

- 比较步骤顺序、控制流和数据处理结构，不被名称或“动作”上的差异迷惑。例如两个流程都执行“读取、校验、转换、保存”，可能存在可复用的共同流程。
- 确认相似步骤是否具有相同语义、约束和变化原因；结构相似只是线索，不足以单独判定需要合并。
- 对真正重复的部分，优先复用已有实现或提取职责明确的函数；差异简单且稳定时，可通过参数表达。不要为了合并少量相似代码引入复杂继承、回调链或大量模式开关。

#### 3.3 if 和 else 中高度相似的语句

- 比较分支内共有的前置步骤、后置步骤和主要流程，识别只在少量值或操作上存在差别的重复代码。
- 若条件只决定一个值，可考虑让分支只计算差异值，再执行共同流程；共同语句也可在行为等价时移到分支外。
- 提取前检查条件求值、执行顺序、副作用、异常、变量作用域和提前返回，确保不增加调用次数或改变触发条件。不能为了消除重复而改变原有行为。

#### 3.4 避免错误抽象

- 判断标准是是否重复表达同一知识、是否必须一起变化，而非出现次数或相似行数。不同业务规则恰好写得相似时，可以保持独立。
- 允许有明确隔离理由的重复，例如独立演进的业务逻辑、生成代码和为清晰表达预期而保留的测试示例；不要要求测试调用生产实现来计算预期结果。
- 建议应说明可合并的共同部分、需要保留的差异，以及最小改动方式。无法证明共同语义时标注待确认，不强行抽象。

### 4. 长函数

核心原则：把函数写短，越短越好；以职责清晰、意图明确为目标。不要因为习惯了长函数，就继续把新的逻辑堆进去。观察设计时关注整体职责和协作，阅读函数时关注每一步的业务含义与细节层次。

#### 4.1 超过 20 行就重点检查

- 将超过 20 行的函数视为长函数检查对象，不等到上百行才提出问题。默认以函数体内非空、非纯注释的代码行计数；独占一行的结构括号不计入，项目已有统计口径时沿用并说明。
- 行数是检查信号，不是唯一判断依据。检查是否混杂职责、难以概括意图、需要同时记住大量中间状态；不足 20 行但存在这些问题的函数也需要关注。
- 不通过压缩多条语句、删除合理空行或注释来“变短”。对于超过阈值的函数，说明可拆分的职责；若保留，说明具体理由，不能只用“看得懂”或“怕影响性能”带过。

#### 4.2 不以未经验证的性能担忧阻止拆分

- 默认优先考虑可维护性，不把性能优化作为组织函数的第一考量。不凭猜测认定函数调用开销足以成为保留长函数的理由。
- 确有性能目标或热点测量证据时，结合约束评估拆分方式；必要时用相关基准验证，不为缩短函数破坏已证实的性能要求。

#### 4.3 避免平铺直叙和混杂层次

- 检查是否把多个业务处理流程全部放进一个函数。按有业务意义的步骤提取函数，让主函数清楚表达流程，而不是展开所有实现。
- 检查是否混合不同层面的细节，例如业务编排与底层解析、存储操作、字段转换交织。将细节收敛到职责明确的函数，保持同一函数中的步骤处于相近的抽象层次。
- 提取的函数应能用准确名称描述意图。避免机械地每 20 行切一段、使用 `step1` 等无含义名称，或把大量局部变量变成参数和共享可变状态。
- 拆分建议必须保留原有执行顺序、错误处理、副作用、事务和资源生命周期；缩短函数不能改变行为。

#### 4.4 警惕“一次加一点”

- 检查本次改动是否继续向已有长函数追加独立职责或分支，不因每次只增加几行就忽略累计复杂度。
- 遵循“让营地比来时更干净”：在获得修改授权时，优先整理当前任务触及的职责，将新逻辑放到合适位置，并做小步、可验证的提取；不要借此扩大为全仓重构。
- 仅自查时指出最小整理范围；没有修改授权时仍只提出建议。

### 5. 大类

核心原则：把类写小，越小越好；通过分而治之降低理解成本，让读者不必同时面对所有细节。拆分大类本质上是设计职责与模块边界，而不只是移动代码或减少文件行数。

#### 5.1 检查职责是否单一

- 方法、字段和整体代码量过多时，检查是否承载多个独立职责，或需要因不同业务原因频繁修改。不要只看单个方法是否短，还要观察整个类的职责与协作。
- 查找只使用某一组字段的方法，以及仅适用于某类对象的字段和行为，判断它们是否形成独立的业务概念。
- 例如用户类同时包含基本信息、普通用户信息和编辑专属信息时，评估把编辑专属的字段与行为提取为 `EditorProfile` 等职责明确的类，由用户按业务关系关联；不要让所有用户都携带无关信息。
- 先确认角色关系：同一用户可能同时具备多个角色，不能仅为拆类就强制改为互斥的继承体系。

#### 5.2 按业务含义和变化方式分组字段

- 检查散落字段是否构成内聚的信息组，例如相对稳定的基本资料、经常更新的联系方式、社交账号等。结合一起使用、一起校验、一起变化的关系判断边界。
- 对有独立含义的信息组，考虑提取 `ContactInformation`、`SocialAccounts` 等对象，并将相关校验与更新行为放到合适位置。只添加字段分区注释不能替代必要的模型拆分。
- 稳定性和变化频率是分组线索，不是唯一依据；不要把所有不变字段或所有可变字段机械放进同一个类，也不要把单个类的一致性约束随意拆散。

#### 5.3 用规模限制促使设计保持清晰

- 统计类的字段、方法数量及主要职责，关注字段或方法不断增加的趋势。团队可约定每类字段数量上限，以触发拆分评估；已有上限时对照检查并说明口径。
- 当前未指定统一的字段数、方法数或类行数上限，不自行编造硬性数字。报告应指出具体职责混杂或字段分组证据，而不是只说“这个类太长”。
- 提取职责明确的小类时，说明应迁移的字段和方法、类之间的协作，以及原有接口、持久化映射和行为约束的影响。优先采用最小必要拆分，避免大量仅转发调用的空壳类或增加跨类共享可变状态。

### 6. 长参数列表

核心原则：减小参数列表，越小越好。与缩短函数、拆分大类一样，目标是编写短小、职责清楚的代码，而不是只把参数藏起来。检查定义和调用方，识别参数持续增加、同类型参数易传错、不同变化原因混杂，以及调用时难以理解的标记值。当前不设固定参数数量上限。

#### 6.1 聚沙成塔：封装有共同含义的参数

- 例如 `createBook(title, introduction, coverUrl, type, channel, protagonists, tags, completed)` 随信息增加不断扩展，应评估引入 `CreateBookCommand` 等参数对象，而不是继续在签名末尾追加字段。这是长参数列表问题，不必等函数体变长才处理。
- 只有参数属于同一概念、有相同变化原因或构成共同约束时，才封装在一起；变化频率是线索，不能把不相关参数塞进万能参数类。存在多个独立信息组时，可分别建模。
- 参数对象不只是字段容器。围绕业务行为评估是否提供有含义的创建方法、校验、默认值或转换行为，集中表达对象的构造约束，减少调用方重复拼装逻辑。
- 不认为变成一个参数就自动消除了复杂度。必要输入仍需提供，构建器也不能凭空减少业务所需信息；重点检查是否改善表达、减少重复、避免无效组合。不要为凑成单参数引入不必要的类或把持久化职责塞进参数对象。

#### 6.2 动静分离：区分稳定依赖与每次输入

- 对 `getChapters(bookId, httpClient, processor)`，确认 `bookId` 是否随调用变化，而 `httpClient` 与 `processor` 是否在同一服务实例中稳定复用。
- 若依赖的职责归属和生命周期合适，可通过构造函数或现有依赖注入机制保存到服务实例，使调用表达为 `getChapters(bookId)`。这属于将稳定依赖纳入软件结构，不是在方法内部每次创建，也不是改为全局可变变量。
- 如果客户端、处理器需要按请求、租户或调用策略变化，不能直接固定为共享依赖。先检查并发安全、隔离要求和资源生命周期，再决定是否迁移。
- 不同变化频率的参数分别处理：稳定依赖归入适当结构，每次变化的业务值保留为输入；多个有独立变化原因的业务参数组分别封装。

#### 6.3 告别标记：移除控制行为的参数

- 检查 `boolean` 等参数是否用来选择不同业务动作，导致调用方只能用 `true`、`false` 表达隐含意图。例如 `editChapter(..., approved)` 若实际选择“仅编辑”或“编辑并审核通过”，可考虑拆为 `editChapter(...)` 和 `editAndApproveChapter(...)`。
- 这种手法称为“移除标记参数”。拆分后的名称应表达真实行为，共同实现按第三条规则复用，避免复制整段逻辑。
- 不是所有布尔值都是行为标记。若 `completed` 表达作品本身的状态数据，不能仅因类型为布尔值就强制拆成多个入口；结合分支、业务契约和调用方式判断。
- 拆分前确认权限、校验、事务与副作用，避免把本来一次原子执行的编辑和审核改成两次独立调用。公开接口变更应说明调用方迁移与兼容性影响。

### 7. 滥用控制语句

核心原则：检查循环和选择语句是否造成过深嵌套、重复分支或难以理解的控制流。它们本身不是坏味道；目标是减少不必要的控制复杂度，降低理解成本。

#### 7.1 嵌套的代码

- 循环内再套条件判断导致的多层缩进是重点信号。先把循环体提取为只处理单个元素的函数（如从 `distributeEpubs` 提取 `distributeEpub`），再处理函数内部的嵌套条件。
- 先决条件检查改用卫语句：条件不满足立即返回，让主流程保持在一层缩进。以“函数至多有一层缩进”为参考评估嵌套深度。
- 消除缩进必须保留原有执行顺序、条件短路逻辑和副作用；把嵌套改写为顺序返回时逐条核对分支语义没有变化。

#### 7.2 不必要的 else

- 检查 if/else if 链是否只是依次判断互斥条件；可改为每个分支独立判断、提前返回，让每个条件完整表达自己的场景。
- 分支逻辑继续变复杂或各分支行为差异大时，评估以多态取代条件表达式，而不是继续拉长分支链。最好在逻辑还简单时消除坏味道。
- 不机械消灭所有 else：分支间共享大量前后逻辑、语言或框架约定要求单一出口时，说明理由后可以保留。

#### 7.3 重复的 switch

- 多处按同一字段做相似分支（如按用户级别计算不同价格）说明缺少一个模型。检查同一组分支是否散落在多个场景中。
- 评估引入该字段的角色模型（如 `UserLevel` 接口及各级别实现），把分支差异变成多态行为，调用方只依赖接口，新增级别不再修改所有分支。
- 以多态取代条件表达式不只针对 switch，等价的长 if/else 链同样适用。分支少且稳定、或项目未采用多态风格时，仍可报告问题但说明权衡。

#### 7.4 用圈复杂度辅助检查

- 圈复杂度是复杂度信号，可用工具检查（如 Checkstyle）；项目已有限制时对照执行并说明口径。卫语句和提前返回可以降低嵌套深度，但不一定降低圈复杂度：判断点未减少时，圈复杂度可能保持不变。不能把减少缩进或移除 else 直接等同于圈复杂度下降。
- 不为降低数字而机械重排代码；复杂度指标的目的是提示检查，判断仍以职责清晰、意图明确为准。

### 8. 缺乏封装

核心原则：构建模型，封装散落的代码。检查连续暴露内部结构的调用链和到处传递的基本类型，判断是否缺少应有的模型；封装应基于行为，而不是让使用者必须了解内部实现。

#### 8.1 火车残骸（过长的消息链）

- 一行内连续多个方法调用（如 `book.getAuthor().getName()`）说明使用者必须了解 Book 和 Author 的内部结构才能写代码，这是失败的封装。数量不断增长的调用链优先报告。
- 用隐藏委托关系处理：由直接持有信息的对象提供表达意图的方法（如 `book.getAuthorName()`），调用方不逐层深入。以迪米特法则为日常指导：只与直接的朋友交谈。
- 转发方法增多是这类重构的常见结果；更根本的改进是回到“这个类应该提供哪些行为”来设计接口，而不是把数据换一种形式继续暴露。
- 区分两种连续调用：内部 DSL 是声明式的“做什么”，火车残骸是“怎么做”的实现细节，抽象层次不同，不把 DSL 风格误报为坏味道。

#### 8.2 基本类型偏执

- 检查有业务约束或行为需求的概念是否只用基本类型表示。价格不等于 double：价格要求大于 0 的校验不应散落在每个使用处，而应收敛到 `Price` 等模型的初始化中。
- 引入模型后继续承接相关行为（如保留两位小数的展示方法），避免同一规则在代码各处重复实现。
- 基本类型不限于语言内置类型，字符串和集合类型同样是高发位置。参考“对象健身操”两条：封装所有基本类型和字符串；使用一流的集合。
- 注意与继承的关联：`Books extends List<Book>` 与用 double 表示价格同源——只看到相同之处而忽略差异。不需要完整集合能力时用组合，不继承集合类。
- 不为每个基本类型机械建类；没有独立约束或行为、只是普通计数或循环下标的值保留基本类型，并说明判断依据。

### 9. 可变的数据

核心原则：限制可变的数据。可变本身不是错误，不可控的变化才是问题。检查暴露修改入口的 setter、随处发生的数据更新，以及本可设计为不变却随意修改的数据。

#### 9.1 满天飞的 Setter

- setter 是缺乏封装的典型：把修改权交给不了解该类的使用者，变化完全不可控。检查字段生成 getter 时是否同时生成了 setter，以及 setter 实际被谁调用。
- 修改数据应通过表达业务行为的方法（如 `book.approve()` 替代 `book.setReviewStatus(APPROVED)`），让所有修改都有受控入口，业务调整收敛在类内部。
- 只在初始化时使用的设值逻辑改为构造函数参数，不以 setter 形式存在；这是移除设值函数重构手法。
- 使用 Lombok 时检查 `@Setter`、`@Data` 是否放开了修改入口：源码里看不到 setter 不代表没有 setter。可在 `lombok.config` 中配置 `lombok.setter.flagUsage = error`、`lombok.data.flagUsage = error` 禁用。
- 并非所有状态变化都要禁止：实体对象的状态演进是业务的一部分，关键是变化有表达业务含义的入口，而不是任何人可随意改字段。

#### 9.2 编写不变类

- 不变类三个要点：所有字段只在构造函数中初始化；方法都是纯函数；需要变化时返回新对象而不是修改已有字段。
- 区分类的性质再动手：值对象设计成不变类；实体对象限制数据变化。不把所有类都机械改成不变类。
- 参考 JDK 演化方向：`Date` 带各种 setter，`LocalDateTime` 初始化后不再变化、操作返回新对象（如 `plusDays`）。新代码优先选择这类不变设计。

#### 9.3 全局数据

- 全局变量和静态可变字段与可变数据同样处理：检查被多少处修改、修改顺序是否可控。评估收敛为实例状态、不可变结构或受控入口。

### 10. 变量声明与赋值分离

核心原则：一次性完成变量的初始化。声明与真正赋值之间隔得越远，初始化与业务处理混杂越严重；用不变性约束代码，让赋值只发生一次。

#### 10.1 声明与赋值分离

- 形如 `EpubStatus status = null;` 声明时赋的 null 是假初始化，真正的值在后续业务处理中才确定。检查变量从声明到获得真实值之间隔了多少业务代码。
- 提取函数让初始化一次完成（如 `final EpubStatus status = toEpubStatus(response);`），声明处即为最终值。“函数开头集中声明变量”是 C 语言时代的习惯，按使用场景就近声明。
- 加 final 是发现此坏味道的实用手段：编译器会指出所有二次赋值位置。能在使用 final 的地方尽量使用，包括局部变量、参数和类字段。
- 语法限制导致的分离用新写法解决：资源关闭场景用 try-with-resources 让初始化一次完成，不再先声明为 null 再在 finally 中处理。
- 循环内重新赋值等确需再次赋值的场景不强行加 final；报告时说明哪些变量必须可变及原因。

#### 10.2 集合的一次性初始化

- 声明空集合再逐个 add 是命令式写法，从声明到可用状态隔着多步。改为声明式一次完成：Java 9+ 用 `List.of(...)`，旧版本可用 Guava 的 `ImmutableList.of(...)`。
- 静态块逐个 put 同理，改用 `ImmutableMap.of(...)` 等一次性声明，消除专门的初始化块。
- 优先使用不可变集合：多数集合创建后只作只读使用，创建后不再添加元素时用不可变实现；确需可变集合时说明原因。
- 以声明式为参考检查代码：描述“做什么”的代码比逐步描述“怎么做”的代码更清晰；其他分步初始化也评估改为一次性声明。

### 11. 依赖混乱

核心原则：代码应该向着稳定的方向依赖。核心业务应比外部接口稳定；检查跨层传递的对象和业务代码中的具体实现，缺少模型时引入模型，把业务与易变细节隔离开。

#### 11.1 缺少防腐层

- 检查 resource 层的请求对象（如 `NewBookRequest`）是否直接传入 service 层。请求对象承载校验和转换，属于接口层；进入核心业务会让业务依赖外部协议，无法保持稳定。
- 反向检查同一个类是否混合多层职责：业务实体上出现传输层注解（如 `@Entity` 与 `@JsonIgnoreProperties` 并存）说明防腐层缺失，实体与传输对象混在一起。
- 引入独立的业务参数对象（如 `NewBookParameter`），由 resource 层完成请求对象到业务参数的转换后再调用 service。两层模型不必字段一致：请求对象多用基本类型，业务参数对象用业务类型（如 `Price`）。
- 两层参数不一致时（如登录态识别出的 userId），在构造业务参数对象时传入必需参数，不为了让请求对象通用而塞进无关字段。
- 依赖方向可用工具守护（如 ArchUnit 把架构规则写成单元测试）；项目已有架构约定时对照检查并指出违反处。

#### 11.2 业务代码里的具体实现

- 检查业务流程中直接出现的具体实现（如业务方法里调用 `feishuSender`）。判断标准：不用它是否还有其他选择？可替换的即时通信工具、Kafka、Redis、MongoDB 等中间件都是具体实现，出现在业务代码中就是坏味道。
- 引入角色接口（如 `FailureSender`）隔离业务与实现，具体实现通过依赖注入提供；高层模块与低层模块都依赖抽象（依赖倒置原则）。
- 检查依赖方向与稳定性是否一致：实现变化只改注入的实现而不改业务代码是对的；业务代码因实现变化而修改即是坏味道信号。
- 项目未使用依赖注入框架时，通过构造函数传入抽象即可，不为此强行引入框架。

### 12. 不一致的代码

核心原则：保持代码在各个层面上的一致性。不一致造成认知负担，类似含义应有类似表达；不甚理想但统一的标准，也比百花齐放更容易理解。

#### 12.1 命名中的不一致

- 同一枚举、同一组常量中含义类似的名称应有一致形式（如 `WEBSITE` 与 `KINDLE_ONLY` 应统一命名风格）。发现不一致时先确认是否表达了不同的业务含义；给不出有效解释的按坏味道报告。
- 名称差异有时代表不同业务角色（如 `XXXService` 与 `BookSender` 的区分）。只有确认含义确实不同时才保留差异，并确认差异在团队理解中成立。

#### 12.2 方案中的不一致

- 检查同一问题在项目中是否有多套解决方案并存：新旧日期时间 API 混用、多个工具库做同一件事（如 Guava 与 Commons Lang 并用）等。
- 方案不一致多来自时间演化或个人习惯。团队已有约定时对照执行；缺少约定时提出需要统一的具体候选方案，不擅自替团队定标准。
- 报告时说明旧方案的具体问题（如 `SimpleDateFormat` 的线程安全问题），让统一约定有依据，而不只是“应该用新的”。

#### 12.3 代码中的不一致（层次混杂）

- 检查同一函数中的语句是否处于同一抽象层次：业务动作与实现细节（构造 HTTP 请求、执行发送等）混在一起是最常见形态，也是长函数的常见根源。
- 提取函数把细节收敛，让每个函数内的语句处在相近层次；提取出的细节若本质上不属于当前业务类，进一步引入独立模型（如 `TranslationEngine`）移出去。
- “如何测试私有方法”这类纠结通常是层次混杂的设计信号：提取为职责明确的公开方法后按公开方法测试，不用反射等技巧解决本不应存在的问题。

### 13. 落后的代码风格

核心原则：不断学习“新”的代码风格，不断改善自己的代码。语言与程序库持续演进，新特性通常提高表达性、减少犯错；检查停留在旧习惯的写法，并结合项目实际版本提出改进。

#### 13.1 用 Optional 表达可能缺失的值

- 可能没有值的返回（如 `getAuthor()` 可能返回 null）评估返回 Optional，让调用方在取值前必须面对“是否存在”的问题，减少忘记判空导致的空指针。
- 团队可约定所有可能为 null 的返回值返回 Optional。语言已有空安全语法（如 Kotlin 的 `?.`）时优先用语言机制。
- 不把 Optional 用于字段、参数等不适合的位置；不会缺失的值不必强行包裹，避免为形式而形式。

#### 13.2 用列表转换取代循环

- 对只做筛选、转换、汇总的循环，评估列表转换（如 Stream 的 `filter`/`map`/`collect`）能否更直接表达意图。循环本身不是坏味道，不仅因使用 for 就报告问题。
- 当操作能与业务过程清晰对应时，优先用简洁的声明式表达；若包含复杂的提前退出、跨元素状态、异常处理或副作用，清晰的循环可能更合适。改写必须保留求值顺序、短路行为与副作用，不能只为使用 Stream 增加理解成本。
- lambda 保持短小，最好一行；复杂转换提取命名函数（如 `toChapterParameter`）。在 lambda 里写大段代码同样是长函数坏味道。
- 已使用 Stream 但 lambda 冗长、流水线职责混杂时，报告具体问题并说明改法。团队是否熟悉某种写法不是判定缺陷的充分依据；结合现有规范和实际可读性判断，不把新语法本身当作改进。

#### 13.3 检查其他落后习惯

- 对照项目语言版本检查旧风格残留：旧日期时间 API（`Date`/`SimpleDateFormat`）、手工关闭资源、声明后置空再赋值等，改为项目版本支持的新写法。
- 建议以项目实际支持的版本为前提；需要升级语言或依赖版本才能成立的改动列为待确认项，不当作可直接执行的修改。
- 同一代码库中多代风格并存会加剧理解难度，与第十二条“不一致”相互印证；建议以团队为单位逐步统一到新风格。

### 14. 谨慎变动与易被忽视的坏味道

核心原则：谨慎地对待接口和实体的变动，限制全局可变状态和隐藏依赖。这里的坏味道或缺少直观的代码形态，或被当作正常习惯；识别靠明确的症状和变化原因，不靠个人审美。每条先说明产生原因，再给出识别方法和应对约束。

#### 14.1 不假思索地增加新接口

- 产生原因：把“新需求 = 加一个接口、加一个服务、加一个状态”当成常规操作，没有回到业务分析新动作与已有动作的关系。接口是系统暴露的能力，一旦提供出去，就不知道什么人会以什么方式使用；事后清理时又会影响依赖方。
- 识别方法：准备对外提供新接口时，先问“真的需要新接口吗”。检查新业务动作能否通过已有业务完成或微调完成：如果新动作与已有动作的后续行为一致，只是起始状态不同（如驳回已审核章节与审核不通过），应复用已有接口，在内部按当前状态设置结果状态。
- 应对与约束：优先让变化留在系统内部，接口与服务的数量不增长；是否新增状态值同样回到业务判断，后续处理一致的状态应统一（如编辑端可查看与否这类差异，确认产品意图后再定）。确实需要新接口时，说明为何无法复用已有业务。

#### 14.2 不假思索地修改业务实体

- 产生原因：有需求就改实体几乎是不假思索的习惯。实体是系统最核心、应最稳定的部分，随意修改必然牵连其他部分调整，让系统难以稳定下来。
- 识别方法：给实体加字段前先问：这个信息是实体本身的属性，还是只是特定场景所需的信息？变化原因不同的信息不应塞进同一个类。例如定时提交章节的调度时间不属于章节实体，应新建 `ChapterSchedule` 之类的调度模型与章节关联；而提交时间本是章节属性（此前与创建时间共用），定时提交出现后就应增加 `submittedAt`。
- 应对与约束：判断标准是字段改变的原因（单一职责原则），不是“要不要动实体”本身。调度时间与实际提交时间是两个概念，系统延迟执行时二者不同，不用提交时间字段兼存调度时间。新增模型时说明它与实体的关联方式和后续同类信息的归属。

#### 14.3 霰弹式修改

- 产生原因：低内聚的直接表现——同一知识或职责分散在多个模块，没有单一、权威的表达，修改时必须在多处做许多小修改。
- 识别方法：观察一次业务变化需要修改的类的数量。每当对某件事做修改，都必须在许多不同的类里做小修改，且容易忘掉其中某处，就是霰弹式修改。它没有直观的代码形态，依赖对“这次改了多少类”的敏感度，可在代码评审和自查时专门清点本次改动的模块。
- 应对与约束：用搬移函数、搬移字段把所有需要一起修改的代码收进同一个模块。与第三条重复代码相互印证：分散常常就是重复表达同一知识的结果。

#### 14.4 发散式变化

- 产生原因：高耦合的直接表现——一个类承担了多个变化方向的责任，不同原因引起的变化都落到同一个模块上。
- 识别方法：观察同一个类是否经常因不同的原因、向不同的方向变化。发现它需要意识到对同一模块的多次修改来自不同原因，敏感度要求更高；可与第四条长函数、第五条大类的职责检查结合进行。
- 应对与约束：先用提炼函数把不同用途的逻辑分开，再用搬移函数把它们分别搬到合适的模块。

#### 14.5 中间人

- 产生原因：过度运用委托和封装，类把大部分职责转手给了其他对象，自己只剩转发。
- 识别方法：检查类接口中只做转发的函数占比，约一半以上函数都在委托给其他类即是中间人。它与过长的消息链（第八条 8.1）互为两端：一个暴露太多，一个包装太多。
- 应对与约束：移除中间人，让调用方直接与真正提供行为的对象协作，或内联琐碎的转发函数。有真实隔离职责的委托（如防腐层、隐藏委托）保留，不机械消除。

#### 14.6 static 函数与变量

- 产生原因：把 static 当成便利的全局访问入口，可能引入共享可变状态，或隐藏对外部资源、环境和生命周期的依赖，导致测试隔离、并发与替换实现困难。无状态纯函数不因使用 static 就难以测试。
- 识别方法：检查 static 字段的实际可变性、写入方和共享范围，以及 static 方法是否访问全局状态、执行 I/O 或隐藏需替换的依赖。区分不可变常量、无状态纯函数与全局可变状态；前两者可以保留，不仅因出现 static 就报告问题。static final 只限制引用重新赋值，不保证其指向的集合或对象不可变。Singleton（见 14.7）若提供全局状态入口，也需检查这些风险。
- 应对与约束：仅对有具体问题的全局状态或隐藏依赖做小步重构：将相关职责放到实例中，由构造函数传入依赖，在对象组装处确定共享方式与生命周期，再逐步迁移调用方。保留合理的静态常量、纯函数和静态工厂；不为去掉 static 而机械增加对象。每步验证行为、测试隔离、并发安全及资源释放，不做一刀切的大改。

#### 14.7 Singleton 模式

- 产生原因：混淆“系统里只有一个实例”和“限制系统只能构建出一个实例”两件事；为全局访问的方便而限制了构造。
- 识别方法：检查私有构造加静态获取入口（如 `getInstance()`）的组合。
- 应对与约束：尽可能不用 Singleton。确实需要共享实例时，把实例创建放到对象组装过程（组合根）中，类本身不限制构造；处理手法与消除 static 类似，移除限制实例唯一的静态函数与字段，保留普通类成员。涉及全局生命周期时说明测试与并发影响。

#### 14.8 命名遗留习惯

- 产生原因：早期编程习惯的遗留：接口加 `I` 前缀、实现加 `Impl` 后缀是没想好命名的偷懒方式，属于用技术术语命名；为省一个字母制造缩写（如 `Txt`）反而造成更大理解障碍，还容易与既有缩写（如事务的 `Tx`）混淆。
- 识别方法：检查接口与实现类的 `I`、`Impl` 前后缀；检查非常用缩写（结合第二条 2.4 的缩写检查）；检查只有一个实现的接口，评估这层接口是否必要——为“预留多种实现”提前分出的接口加实现，往往是不必要的层次。
- 应对与约束：接口名表达职责（`ItemService` 而不是 `ProcessItemService`，“处理”是过于泛化的动词）；实现类按真实差异命名，存储方式差异应体现在存储层，而不是从服务层就分叉出 `ProcessTxtServiceImpl` 这类实现。涉及公开 API 时说明兼容性影响。

#### 14.9 用注释代替清晰的代码

- 产生原因：不把代码本身写清楚，靠注释补救；或把“写注释”当成不加区分的习惯性要求。
- 识别方法：把注释当坏味道的提示。检查注释是否在解释代码本身难以理解的“怎么做”；注释应留给确实无法用代码陈述清楚的内容（精巧算法、特殊技巧、外部约束）以及“为什么这样做”的业务背景。大多数普通代码不需要注释。
- 应对与约束：先竭力把代码写到不需要注释，注释是最后的选择，不应是主力。保留的注释说明存在原因，不复述实现。

#### 14.10 潦草的项目文档

- 产生原因：普遍忽略文档，或把 README 当 blog 写个人心得，信息的有效性很差。
- 识别方法：README 应提供项目背景：项目是做什么的、当前状态、如何入手。信息量过少（只有构建命令）或内容与使用者无关都算问题。此条针对自查涉及的项目文档，不针对代码本身。
- 应对与约束：对照项目用途和使用者需求，报告范围内的文档问题并提出具体改进建议，无需以文档修改授权作为报告前提；实际修改须在用户已授权的任务范围内。仅请求自查时不修改文档，也不因发现文档问题扩展任务范围。

## 输出要求

只报告有上下文依据的问题，按实际影响排序，给出位置、问题类别、原因和最小改进建议。

- 命名问题：给出现有名称和建议名称，解释如何体现真实行为、业务角色或准确的英语表达。无法确认的业务词义明确标注待确认。
- 重复代码：列出相关重复位置，说明重复的知识或流程、同步维护的风险，以及可提取的共同部分和应保留的差异。
- 长函数：给出函数位置、行数及统计口径，说明混杂的业务职责或细节层次、建议提取的步骤及边界；有理由保留超过 20 行的函数时简要说明。
- 大类：给出类位置、字段与方法数量及统计口径，说明混杂职责或字段分组证据、建议提取的类及其字段和行为，并指出必要的协作与兼容性影响。
- 长参数列表：给出函数位置、参数数量和代表性调用，指出可封装的业务参数组、可迁移的稳定依赖或可移除的行为标记，并给出建议签名及行为、生命周期和兼容性约束。
- 滥用控制语句：给出位置、嵌套深度或分支结构，说明可提取的单元素操作、可改写的卫语句与提前返回、可多态化的重复分支；使用圈复杂度时说明统计口径。
- 缺乏封装：给出调用链或基本类型使用位置，说明暴露的实现细节或缺失的业务约束，建议隐藏委托的入口方法或应引入的模型及其承接的行为。
- 可变的数据：给出 setter 或可变字段位置及其调用方，说明修改入口与影响范围，建议表达业务行为的方法、构造函数参数或不变类方案。
- 变量声明与赋值分离：给出变量位置、声明与真正赋值之间的间隔代码，建议一次性初始化的写法或声明式集合初始化，并指出适合加 final 的位置。
- 依赖混乱：指出跨层传递的对象或业务代码中的具体实现，说明当前依赖方向与稳定性的偏差，建议引入的防腐层模型或角色接口及注入方式。
- 不一致的代码：指出不一致的具体位置与应对照的参照物，建议统一后的形式，或需要团队确认的命名、方案与层次约定。
- 落后的代码风格：指出旧风格位置及问题，给出项目当前版本支持的新写法；需要升级版本才能实施的标注待确认。
- 谨慎变动与易被忽视的坏味道：接口与实体变动给出业务分析依据和最小改动范围；霰弹式修改、发散式变化列出变化影响的模块与变化原因；static、Singleton 指出具体的共享状态或隐藏依赖风险及最小改进路径；中间人给出转发函数占比；注释与文档指出可由代码或 README 更好表达的内容。

仅有个人风格偏好时不列为坏味道；未发现问题时如实说明检查范围内未发现明显问题。
